# Provider 怎样声明目标支持，并把配置转换为产物

状态：Provider 框架契约经独立 Review 修订复核 PASS；已有固定内置后端子集，具体范围见[首期执行契约](implementation-v0.md)与[验收记录](implementation-validation.md)，本文的长期框架不代表全部实现。日期：2026-10-21。

本文承接[平台机制说明](./how-proxylang-handles-platforms.md)，用 Markdown 描述构建后端的契约，不提供实现代码。这里的 Build Provider 是编译后端，不是客户端运行时的代理订阅 provider；后者是平台程序中的一种资源。

## 从一个容易误解的支持声明开始

“支持 sing-box”至少可能表示三件事：认识这个内核的配置结构、能转换当前用户配置、曾在某个版本上验证过实际行为。这三个结论不能合并成一个布尔值。

我们的设计让 provider 先声明可处理的目标，再针对完整程序制定转换计划，最后单独报告验证结果。一个版本出现在目标列表里，不代表它支持语言中的所有功能；一次编译成功，也不代表配置已在用户设备上运行。

## 1. Provider、Program、Build Target 分别是什么

| 概念 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| Build Provider | 一个内核的程序模型、版本规则、能力判定、转换及序列化 | 选择用户业务策略、自动改成另一个内核 |
| Platform Program | 用户希望这个平台执行的完整处理过程，引用共享资源和策略 | 声明某个版本天然支持所有功能 |
| Build Target | 选择一个程序，并锁定内核、平台、版本和输出模式 | 靠填写 capabilities 绕过 provider 校验 |
| Build Host | 加载可信配置、调度 provider、资源及秘密解析、原生校验进程、文件提交 | 猜测平台规则的语义 |

一个 sing-box 程序由 sing-box provider 编译；共享策略在程序中被实例化。不能把 target.engine 改成 surge，就让同一份 sing-box 原生程序自动变成 Surge 配置。

一个程序可以对应多个版本目标；一个内核也可以有多个用途不同的程序，例如桌面和网关。多个目标引用同一个源程序时，使用同一份不可变快照，分别创建转换上下文，不共享可变 AST、运行时缓存或客户端选择状态。

首期内置 provider 与编译器一起发布。每个 engine 只有一个 provider；不动态下载插件，不按安装顺序覆盖内核处理器。以后开放第三方 provider 需要另外设计加载、冲突及信任边界。

## 2. 用户怎样描述 Build Target

目标的名字代表一次输出，目标属性代表需要输出给谁。

| 字段 | 含义与规则 |
| --- | --- |
| id | 构建内唯一的输出身份；限制为小写字母开头及字母、数字、连字符、下划线，不直接接受文件路径 |
| program | 必填的程序引用；程序声明的 engine 必须与目标相同 |
| engine | 明确区分 surge、mihomo、sing-box，以及未来单独实现的 clash 等内核 |
| platform | 目标运行平台，不是执行编译器的主机平台 |
| version | 精确版本；首期不接受 latest 或浮动范围 |
| build | 只有该 provider 的版本规则需要区分发行构建时才使用 |
| distribution | 可选，选择 provider 已知的发行构建描述，包含编译特性；不是任意支持能力开关 |
| clientProfile | 可选，选择已登记的客户端约束；内核支持与客户端约束取交集 |
| mode | fragment 或 standalone；默认 fragment，standalone 必须满足完整运行前提 |

例如，家用路由程序可以同时构建到两个 mihomo 版本，网关程序同时构建到两个 sing-box 版本，电脑程序同时构建到两个 Surge 版本。它们是同一种目标矩阵机制，没有 Surge 专用分支。

所有版本例子仅说明结构，不在本文中发布实际支持清单。实际支持清单由 CLI `targets` 和 `src/compiler.ts` 中的版本目录给出；精确目标的验收证据另见验收记录。

输出按 target ID 分目录。相同 engine、不同 version 不会覆盖同一个文件；相同版本、不同程序也可以独立输出。实际输出路径由 host 从合法 target ID 分配，provider 只能返回 bundle 内的相对路径。

fragment 是声明了组合边界的片段，必须列出外部引用、入口元数据和 DNS 等前提，并按片段 schema 校验。外部引用必须显式声明，不能把拼错的名称当成“以后会补齐”。standalone 则必须将这些前提全部绑定到具体程序资源。未组合成完整配置的 fragment 不能通过完整配置的原生检查，报告为 not-run，并保留未验证的组合前提；如果构建要求原生检查必过，则此时直接阻止发布。

没有定义组合契约的 fragment 类型暂不支持。片段的行为保证只在列出的前提成立时适用；目标本身无法提供前提时仍须阻塞，不能用外部依赖声明绕过已知不支持。

## 3. Provider 声明哪些信息

Provider Manifest 是随实现发布、可检查的数据目录。

| 声明 | 目的 |
| --- | --- |
| providerId、providerVersion、providerApiVersion | 区分实现版本及 host 协议兼容性 |
| engine、programSchemaVersion | 说明接受哪种平台程序；不能把程序 schema 版本与客户端版本混用 |
| targetProfiles | 列出平台、发行构建与已知版本覆盖范围 |
| featureRules | 描述能力条件、选项组合、依赖、限制和证据 |
| loweringRules | 把可支持的语义构造关联到实际转换处理器 |
| outputSchema、serializer | 指定原生结构校验与输出格式实现 |
| validatorDescriptors | 描述可选原生检查器的身份、参数模板及适用目标，不自行启动进程 |

首期 providerApiVersion 和 programSchemaVersion 都按精确匹配加载；不兼容就报错，不默默兼容未知字段。用户描述对象沿用 type 命名，不使用 kind。

Manifest 引用的处理器必须在 provider 实现中注册。host 加载时校验引用、重复 ID 与区间结构；声明了一项转换却没有处理器，属于 provider 错误，不能推迟到用户输出文件时才发现。

元数据只能证明声明完整，不能证明处理器正确。每项支持声明还需要后续的转换测试及相应原生验证证据。

## 4. 先判断版本是否在知识范围内

Provider 自己定义版本解析器。它必须给出规范化结果、比较规则和预发布处理方式，不假设所有客户端都遵守完全相同的 SemVer 规则。不同 engine、不同平台之间不比较版本大小。

每个 target profile 使用明确的精确版本集合，或有上下界的版本区间。区间必须有依据，不能因为较早版本通过测试就声明一直支持到未来。预发布版本默认不属于稳定版区间，需要独立条目。

选择流程固定为：匹配 engine，校验 platform 和 distribution/clientProfile，再解析 version/build，最后选取唯一的版本 profile。没有匹配时区分“已知不支持”和“尚无知识”；匹配多个条目则报 provider 目录歧义，禁止用隐式优先级猜测。

可选 build/distribution 未填写时，只能选择目录中唯一且明确的默认发行构建；存在差异且无法确定则报缺少目标身份。用户自行声明“开启某项能力”不能替代发行构建证据。

例如，Surge 官方会分别列出某项协议在 macOS 与 iOS 上的最低版本，这说明版本条件必须与平台绑定。[Surge 协议目录](https://manual.nssurge.com/policies/overview.html)

“目标已知”只是允许进入分析阶段。接下来仍然要检查程序实际用了哪些功能。

## 5. 能力是语义要求，不是字段白名单

共享片段和平台节点都有 schema。schema 会枚举每个节点与字段引入的语义要求；provider 不能仅扫描自己认识的字段，然后把其余内容忘掉。未知节点或未知字段首先作为 schema 错误处理。

省略字段也必须有语义。validateProgram 按程序 schema 的稳定默认值生成规范化输入，保留默认值来源；这些值同样进入能力分析和消费检查。转换器只有证明目标默认值相同时才可以省略原生字段，否则必须显式编码。用户希望跟随目标原生默认行为时，须在允许该选择的字段上显式声明；analyze 解析并记录每个目标的已知行为和差异。原生默认值未知则阻塞，不能靠不写字段绕过检查。共享语义要求稳定行为时，不允许选择目标原生默认。

一个能力项包含稳定 ID、影响类别、输入选项约束、目标条件、与其他能力的依赖或冲突，以及相应的转换规则 ID。能力 ID 按命名空间区分共享语义与平台机制，例如共享域名后缀匹配、共享终结路由、sing-box 非终结解析动作。

“支持 Trojan”本身不够，还要判断具体 TLS、传输、网络协议和拨号依赖组合。相同节点的 TCP 支持不等于 UDP 支持；策略组的 initial 成员可用也不等于所有可选成员都满足要求。

每个能力声明都有两份独立信息：

- **实现判定**：原生支持、通过已知转换支持、已知不支持、未知。
- **证据状态**：文档／源码依据、核对日期、已测试的精确目标、验证类型与测试标识。

在一个有证据的格式区间内可以生成配置，但“本次目标未跑原生检查”必须保留为 not-run。编译支持不能直接升级成运行验收结论。

展示字段可以声明为可省略，但必须给出安全省略规则。省略前仍检查字段类型、引用及冲突；不能省略整个包含行为配置的节点。代理、DNS、路由、权限和资源生命周期相关能力不允许标成展示信息。

## 6. Support Decision 应回答具体问题

能力分析不是一个 supports 函数返回 true，而是为每个使用点给出决定。

| 决定 | 意义 | 后续动作 |
| --- | --- | --- |
| native | 目标有同一语义的原生表达 | 选择对应编码规则 |
| lowered | 需要转换，且已知规则能保持契约 | 记录转换步骤及其前提 |
| omit-presentation | 已知只损失允许省略的展示信息 | 记录字段与 warning |
| unsupported | 有依据说明无法满足 | 产生阻塞诊断 |
| unknown | 现有目录不足以判断 | 阻止构建，不尝试原样透传 |

每项决定都带目标身份、源节点 ID／字段路径、能力 ID、原因、证据引用。不得输出秘密值。原生支持也需要编码处理器，并不是不经检查地复制用户字段。

同一使用点若存在多个候选转换，规则必须声明互斥适用条件；运行时仍出现多个匹配就报歧义。首期不做成本搜索，不随机挑选“看起来最接近”的转换链。

requirements 约束的功能不能被省略；warningsAsErrors 会把 warning 提升为发布阻塞，但没有反向把行为错误降为 warning 的开关。

warningsAsErrors 只作用于活动批次切换前的诊断。发布后的维护警告不追溯阻止已经完成的提交，见第 12 节的退出状态约定。

用户显式限定给其他目标的内容可标记 not-applicable，记录目标选择原因后不进入当前程序实例。它不是能力不支持，也不能被 provider 用来排除当前程序中无法转换的节点。未选择的分支仍需通过语言 schema 校验；其网络能力只对实际选择它的目标检查。

## 7. 先做转换计划，再真正转换

分析阶段产生 Conversion Plan。它针对一个具体目标、一份固定程序和一组固定资源，不是可随便换目标继续执行的通用计划。

计划记录：目标与 provider 身份、程序 schema 版本、输入快照与资源锁标识、每个使用点的决定、选定处理器、处理次序、辅助资源、引用重映射、诊断和源映射。秘密仍为 token，不包含明文或秘密值摘要。

首期计划只在当前构建进程内使用，以不可变快照对象身份绑定；不提供序列化计划的恢复执行或跨进程缓存。非敏感摘要用于诊断追踪，不作为秘密或身份一致性的替代。这样避免 plan 使用旧资源而 emit 读取新配置。

计划必须满足三个不变量：

1. 每个语义节点和行为字段都被某个转换步骤消费，或明确诊断阻塞。多节点转换可以整体消费一个片段，但不能遗漏内部动作。
2. 每个被省略的内容都有独立的展示省略记录；不能把空输出当成合法的隐式省略。
3. 每个生成引用都能追溯到用户资源或计划内的辅助资源；辅助资源命名由统一分配器生成，不能覆盖用户资源。

Lowering 的实现单位可以是单节点、共享片段或整个平台子图。需要一起处理才能保持语义的内容必须整体规划，不能依次局部改写再希望最终一致。

每条转换规则有输入模式、前置条件、输出模式和保证。规则的执行顺序是 provider 明确声明的有限阶段 DAG；加载时拒绝环，执行时不靠反复重写直到“似乎稳定”。生成的辅助结构不自动重新进入共享语义转换阶段。

host 调用一次 lower，provider 内部按计划调度 DAG，不允许处理器临时改换转换路径。每阶段声明输入表示版本、输出表示版本及允许读取／消费的区域；输出是新的不可变表示。同一输入表示上的消费所有权必须互斥，只读依赖可共享。片段转换消费内部动作后，单节点规则不能再次消费这些动作；无法划分时必须选择一个整体转换规则，否则报告 provider 歧义错误。

跨阶段再次处理只允许通过显式数据流：后阶段消费前阶段产出的新节点，并保留原始来源。辅助结构在计划中指定生产阶段及最终编码阶段；未接入编码路径、未消费、重复消费、表示版本不匹配均失败。最终 AST 校验复核这些记录；这保障结构覆盖，语义保证仍由各规则契约和测试承担。

## 8. Host 与 Provider 的调用边界

| 阶段 | 输入 | 输出与失败边界 |
| --- | --- | --- |
| resolveTarget | manifest、目标声明 | 唯一规范化 Target Profile；身份缺失、未知版本或歧义即失败 |
| validateProgram | 不可变程序、共享实例与资源锁 | schema、引用、作用域和顺序校验结果 |
| analyze | 已验证程序及 Target Profile | 完整 Conversion Plan 与诊断，不写文件、不联网 |
| lower | 当前进程绑定的计划与输入 | 目标版本原生 AST、源映射、辅助资源描述 |
| validateOutput | 原生 AST、计划与目标 schema | 必填字段、名称、引用、版本限制及计划覆盖复核 |
| serialize | 已通过校验的 AST | 带秘密占位段的 Artifact Template Bundle |
| materialize / native check / publish | host 提供秘密及受控环境 | 最终文件、独立验证状态及整批提交结果 |

host 检查每个阶段的错误后才推进，不能只看最后有没有生成文本。lower 声明消费情况与计划不一致、输出出现未规划的语义内容，均属于 provider 错误；不能变成用户 warning。输出校验不是语义正确性的自动证明，关键保证仍需要测试。

validateProgram 的产物包含已补全默认值的不可变规范化程序，analyze 和 lower 仅使用这个结果，不回读用户原始对象。

provider 不读取环境变量、不下载订阅、不启动内核、不把文件写到用户指定位置。host 显式提供锁定资源；资源内容缺失时失败。程序作者的 TypeScript 本身属于可信构建代码，纯编译边界不宣称可以隔离恶意代码。

秘密模板不是简单字符串替换。它保留目标格式的结构化敏感值槽和已登记的上下文编码方式，例如 JSON 字符串、YAML 标量或 Surge 配置参数；host 使用配套的可信编码器生成值，未知编码上下文拒绝。实际值的格式约束在 materialize 时检查，失败即停止该目标，不将明文交给诊断系统。

host 在本次构建首次实际需要某个 token 时解析一次，并在整个批次内复用该值；并发目标也共享这次解析结果。不同目标确实需要不同值时使用不同 token。检查与发布使用同一份已物化文件，不在检查后重新解析或重新渲染。秘密轮换需要重新构建。本轮完成、失败或取消时释放内存引用并清理临时物化文件；不承诺 JavaScript 垃圾回收可做到物理内存清零。活动产物的秘密按输出文件生命周期管理。

原生检查器使用 provider 目录里的固定程序身份与参数模板，host 按目标核对版本后通过参数数组启动，不用 shell 拼接。检查器可能回显输入，输出先捕获，仅允许提取不含用户值的诊断字段；不能可靠提取时只报告状态。超时或取消必须终止并回收本次检查进程与临时资源，不接管用户运行中的客户端。

## 9. 一个版本转换怎样落地

以 sing-box DNS 格式变化为例，官方迁移文档说明 1.12 引入新的 DNS server 结构。这个事实可以帮助建立版本边界，但不能据此自动证明所有旧配置都有等价新表达。[sing-box 迁移文档](https://sing-box.sagernet.org/migration/)

假设平台程序明确要求一个固定 IP 的 UDP DNS 上游，且相关解析出口、默认值及依赖已经确定：

1. schema 把上游传输、地址、端口和解析路径识别为能力要求。
2. provider 对已登记旧目标选择旧 DNS 编码规则，对已登记新目标选择类型化 DNS 编码规则。
3. 两条规则分别检查约定能否保持。涉及引导解析或出口行为而无法对应时，不只改字段名继续输出。
4. 计划记录同一个源资源分别映射到两个目标的哪些结构，输出各自的 schema 校验结果。
5. 在精确版本的测试中检查 DNS 请求实际去了哪里，而不只比较 JSON 快照。

这种设计把版本判断集中在 provider 目录和转换规则里。用户不必在每个 DNS 字段旁写版本判断；真正需要不同网络行为时，用户仍然要显式选择不同的程序变体。

## 10. 一个无法转换的例子怎样处理

某段共享策略要求：公司域名命中后交给指定组，失败不能直连。但目标组有成员不支持 UDP，目标内核又可能在 UDP 不支持时继续向下匹配。

mihomo 官方规则说明中就存在这种继续匹配行为。[mihomo 规则优先级](https://wiki.metacubex.one/en/config/rules/#priority)

此时 provider 分析的是整条可能路径，包括规则允许的网络、组成员、后续规则及拨号依赖。只检查“存在 DOMAIN-SUFFIX 和代理组字段”是不够的。

如果有已验证的转换可以保持终结契约，计划可以选择该转换；否则给出 unsupported。动态 provider 未来成员的能力无法确认时，不能用当前快照证明一直满足。用户可以限定流量范围、改用符合要求的组，或者显式使用平台原生语义；编译器不代替用户选择。

对于域名不存在、嗅探失败或 DNS 不返回结果，能力分析也不能假设有数据。共享契约必须规定缺失行为；没有完整契约的共享能力不能加入支持目录。完整 DNS 和更多共享片段接口仍是后续设计，不因 provider 框架成立就自动获支持。

## 11. 订阅 provider 在这里处于什么位置

运行时订阅 provider 是程序节点，Build Provider 只负责编译它的声明及消费者引用。客户端负责实际下载、更新和缓存；构建器不接管这些运行时资源。

构建期订阅导入则由 host 的显式资源更新流程完成，结果进入资源锁，编译阶段只读固定内容。两者的生命周期不同，转换规则不能把运行时订阅降级为静态列表。

如果目标不支持指定的运行时机制，报告该节点不支持；用户明确选择静态方案后，才能使用另一个构建期资源。本文不定义订阅格式解析器或刷新协议。

## 12. 产物和支持报告由谁负责

provider 返回 bundle，不自行发布。bundle 包含主配置、必要辅助文件、源映射与诊断。所有路径必须是规范化相对路径，host 拒绝绝对路径、父目录跳转、重复路径及越界链接。

本设计沿用且在此明确以下发布契约：全部选定目标在一个新 generation 完成，使用输出根目录独占锁，最后一次原子切换 active.json。任一目标失败则不更新活动批次；单目标构建只发布该次选定目标，不暗中混用历史输出。提交后清理失败应报告警告，不能谎报未发布。

CLI 退出状态固定区分：0 为已发布且无维护失败（允许未被提升的构建 warning）；1 为未发布；2 为已发布但后续维护失败。报告同时携带 published 布尔值和 generation ID。退出码 2 不表示需要重做或回滚构建，host 可在后续持锁清理流程重试维护；退出码 1 才表示活动批次未更新。warning 提升检查必须在原子提交前完成。

秘密目录和文件在创建时使用受限权限，生成报告不含秘密值；旧 generation 及崩溃遗留由 host 在持锁且确认非活动后清理。读取／导出使用共享锁完成固定 bundle 的复制，避免与清理竞态。原子提交、进程回收与文件清理由 host 实现，不分散到多个 provider。

支持报告分开列出目标知识状态、逐项能力决定、已应用转换、省略警告、原生检查状态和行为测试证据。当前构建未运行的验证不能借历史测试标记为 passed；历史证据单列其精确版本与测试标识。

## 13. 怎样增加一个新 Provider 或新版本

增加新内核时，需要明确程序 schema、支持目录、语义能力、转换规则、输出 schema、序列化器和校验器描述。仅增加一个 JSON/YAML 输出器不算完成 provider。

增加版本时，先调查该版本改变了哪些格式和语义，再添加唯一的 target profile。没有变化可以复用处理器，但不能跳过能力证据与边界测试。若已知版本撤销支持，更新目录并明确诊断，不保留一条过宽的“最低版本以上都支持”。

增加功能时，从语义契约和负例开始，再实现处理器与支持条目。至少测试不支持、未知、支持及冲突四类情形；有版本边界时覆盖边界两侧。没有实现的条目不得出现在可执行支持目录中。

## 14. 实现与验收顺序

第一步实现 host/provider 协议、目标解析和完整诊断，使用最小静态节点与分流片段验证声明、计划和输出是同一条链。第二步选择每个内核的精确目标版本，接入真实原生检查与关键网络行为测试。第三步才扩展 DNS、endpoint、动态 provider 等机制，先补各自的语义契约。

必要验收包括：

- 同一程序对同内核同平台的两个版本分别产生正确计划和独立产物；没有跨目标 AST 污染。
- 未知版本、预发布、重叠 profile、错误发行构建、程序与目标内核不符时拒绝构建。
- schema 中未知字段、未消费行为节点、丢失引用、未注册处理器或多条转换同时匹配时明确失败。
- 原生支持与转换支持都有输出和行为用例；不同网络路径、缺失元数据和动态成员不能绕过契约。
- 展示省略输出 warning；required 和行为能力错误不能降级；warningsAsErrors 阻止整批发布。
- 秘密包含引号、逗号、换行等字符时正确编码或明确拒绝，不能注入额外原生配置；日志和检查器输出不泄露内容。
- 原生检查器版本错误、超时、取消和崩溃时有明确状态，进程与临时文件可回收。
- 提交失败不出现半批更新；旧秘密清理与读取锁的并发行为可验证。

以上是后续实现验收要求，不是本轮已通过的测试。本轮只完成设计；具体支持清单、完整共享策略及各平台 schema、真实转换器和运行验收尚未完成。
