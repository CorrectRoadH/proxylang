# 一份代理配置，怎样面对三种不同的世界

我们希望用 TypeScript 管理 Surge、Clash 系内核和 sing-box 的配置。最直接的想法是：定义代理节点、策略组和分流规则，然后分别输出配置文件。

这个想法能解决一部分问题。比如同一个代理服务器地址，不应该在三份配置里分别维护；一组公司域名，也不应该每次新增后手工同步。但当配置开始涉及 DNS、协议嗅探、动态订阅和 HTTP 改写，问题就变了：有些区别来自配置格式，有些区别来自软件处理流量的方式。

proxylang 的设计从这里展开：共享可以共享的内容，让每个平台保留自己的处理过程，再由编译器负责把这些内容落实到具体版本。

本文解释这一设计方向，不定义最终 API。文中的处理过程是语义示例，不代表相关后端已经实现或完成兼容性验证。

编译后端怎样声明版本支持、判断能力并执行转换，继续阅读 [Build Provider 设计](./build-providers.md)。

## 从“公司域名走代理”开始

假设我们同时维护一台使用 Surge 的电脑、一台使用 mihomo 的路由器，以及一台使用 sing-box 的网关。

三处都需要知道哪些是公司域名，也都需要公司出口的连接信息。它们可能还有共同要求：这些域名必须走公司出口，连接失败时不能改为直连。

这里至少有三种不同的内容：

| 内容 | 例子 | 是否应该共享 |
| --- | --- | --- |
| 资源事实 | 公司域名列表、代理服务器地址、认证信息的引用 | 可以共享，但实际协议支持仍要校验 |
| 网络策略 | 公司域名走指定出口，失败不直连 | 可以共享明确的行为约定 |
| 平台执行方式 | 从哪个入口接收流量、何时嗅探、使用哪个 DNS、如何配置 HTTP 处理 | 由各平台具体描述 |

如果把这些内容全部写进一个巨大的通用配置对象，用户很快会遇到大量“这个字段只有某个平台能用”的例外。如果完全分开，又会退回维护三份重复配置。

我们的处理方式是把共享资源和策略提取出来，让完整的平台配置引用它们。修改公司域名只需要修改一处；网关是否需要嗅探，则由网关自己的配置决定。

## 同样叫 rule，执行方式可能不同

Surge 的常见分流方式是：请求匹配一条规则，再交给对应策略。策略可以是代理、直连、拒绝，也可以是策略组。这很适合表达“什么流量交给哪个出口”。[Surge 策略说明](https://manual.nssurge.com/policies/overview.html)

sing-box 的路由规则还可以表达处理步骤。一次匹配可以触发协议嗅探、解析目的域名，或者设置路由选项，然后继续执行后面的规则。它同时具有终结动作与非终结动作。[sing-box 路由动作](https://sing-box.sagernet.org/configuration/route/rule_action/)

考虑一个网关场景：入口接收到连接，先尝试识别协议，再在需要时解析目的地址，最后根据得到的信息选择出口。后面的规则能够看到什么信息，取决于前面的步骤做了什么。

如果我们只提供一张“条件对应出口”的表，嗅探和解析就只能变成塞在规则前后的特殊选项。配置稍微复杂一点，用户便需要不断指定“把这个步骤插到那条规则之前”。程序的实际顺序反而变得难读。

因此，平台配置应该直接拥有自己的执行顺序。对于 sing-box，用户能够按其原生语义组织路由步骤，把共享分流策略放在合适的位置。对于 Surge，用户组织的是对应平台支持的规则与处理机制。平台步骤不需要伪装成普通的出口选择。

共享策略在这里更像一个可以嵌入的分流片段。它有自己的顺序，但不偷偷接管整个程序，也不自动附加一个会截断后续处理的最终默认动作。整个程序的最终处理方式由平台配置明确指定。

## 共享一条规则，也要共享它的前提

“匹配公司域名”看起来很简单，但连接到达时一定带着域名吗？

有些入口能直接提供域名，有些流量只带目的 IP。域名也可能来自协议嗅探或地址映射。即使最后写出的条件都叫“域名匹配”，它们看到的输入也未必一样。

所以，共享策略不能只有条件和动作，还需要说明它依赖什么信息。例如，一段策略只使用已经存在的域名，不要求编译器主动嗅探；另一段策略需要目的 IP，并且允许通过指定的解析路径获得它。

平台配置负责满足这些前提。编译器检查策略放置的位置是否合适、目标是否支持所需机制。如果不能确认，就指出缺少的前提，而不是偷偷加一个全局嗅探开关或改用系统 DNS。

这里还需要区分“配置了机制”和“每个请求都能获得信息”。嗅探可能失败，域名也可能缺失。策略必须定义信息缺失时的匹配结果；编译器不能因为看见了嗅探步骤，就保证所有请求都会带域名。

这样，共享策略表达的行为才有边界：对于符合约定的输入，各目标应得到一致的结果；不同入口产生的输入差异，则留在平台配置中明确说明。

## 代理节点可以共享，但不必把所有资源都叫 proxy

对于连接远端代理的常见协议，服务器、端口、认证和 TLS 等信息有很大复用空间。proxylang 可以保存一份连接描述，再由目标适配器生成相应节点。

不过，协议名称相同并不意味着全部参数组合都支持。某个目标缺少指定传输方式或 TLS 能力时，仍然需要拒绝构建，不能只保留服务器地址、丢掉其余选项。

sing-box 的 endpoint 则更直接地说明了资源模型的差异：它可以同时具有入站和出站行为。这样的资源不能完整地解释为一个“连接到远端服务器的代理节点”。[sing-box Endpoint](https://sing-box.sagernet.org/configuration/endpoint/)

我们的处理方式是保留平台资源。sing-box 配置可以拥有 endpoint，并在它支持的位置引用它；共享层只接触经过明确定义的出口能力，不把整个 endpoint 拆成两个互不相关的虚构对象。

资源归属也随之清楚：共享定义是可复用的描述，每个编译目标得到自己的实例；平台资源只属于所在的平台程序。两个目标不会因为引用同一份描述，就共享客户端运行时状态、缓存或连接。

## DNS 要单独描述，因为它处理的是另一类请求

流量路由决定连接去哪里，DNS 处理决定查询如何执行、答案如何产生。两者有关联，却不能共用一张万能规则表。

在 sing-box 当前文档中，DNS 甚至可以先执行查询，把响应保存下来，再交给后续规则判断。相关动作有自己的版本要求。这已经超出了“给一个域名选择 DNS 服务器”的简单模型。[sing-box DNS 动作](https://sing-box.sagernet.org/configuration/dns/rule_action/)

因此，我们共享域名列表等数据，但不直接共享 DNS 和连接路由的动作。平台配置分别描述这两个处理过程，并明确它们如何关联：代理服务器域名怎样解析、某次解析通过哪个出口、是否需要引导解析，以及解析失败如何处理。

同一份公司域名列表可以用于“公司流量走公司出口”，也可以用于“公司域名交给内部 DNS”。这是复用数据，不是把两种不同的行为视为一回事。

对于完整 DNS 过程，目前先保留平台机制。只有某一部分行为能明确写出共同约定，并在不同目标上验证一致时，才把它提升为共享能力。这样不会因为急于统一几个字段，遗漏真正影响网络行为的解析路径。

## 动态订阅与静态节点，不能在编译时悄悄互换

用户写下一个订阅地址，可能表达两种需求：现在读取它，把节点放进本次构建；或者让客户端运行期间持续更新它。

这两种方式生成的节点在某个时刻可能一样，但资源生命周期不同。前者的内容由构建固定；后者以后还会改变，涉及更新周期、缓存、失败处理与组成员变化。mihomo 的 proxy-provider 就属于需要保留这些运行时机制的配置。[mihomo proxy-provider](https://wiki.metacubex.one/en/config/proxy-providers/)

我们把两种方式分开表达。构建期导入可以成为共享资源，记录来源和内容摘要；运行时 provider 由平台程序持有，并连接到该平台的组或路由机制。

如果另一个目标没有对应的动态机制，编译器不能自动下载一次后宣布转换成功。用户可以明确选择静态快照作为该目标的替代方案，构建报告也应说明它已经失去运行时更新能力。

## HTTP 改写保留在它实际发生的地方

Surge 的 URL、Header、Body 改写和脚本处理属于 HTTP 处理机制。HTTPS 内容要进入相应处理，还涉及 MITM 前提；这些不是普通的连接出口规则。[Surge HTTP 处理](https://manual.nssurge.com/http/overview.html)

因此，Surge 平台配置应当直接描述 HTTP 处理、相关资源和前提。我们不会把“改写这个 URL”翻译成“匹配这个域名并路由”，也不会为了输出到另一个目标就只发一个 warning 然后删掉它。

其他目标是否需要同样的业务效果，由用户在那个目标的程序中明确选择。如果某个效果对所有目标都必不可少，就把它声明为整体要求；不能满足的目标构建失败。如果它本来就只服务于电脑上的 Surge，则明确限定到该程序，其余程序不承担这个要求。

## 平台程序与共享策略怎样组合

到这里，proxylang 的结构可以用三个部分描述。

**共享定义**保存节点连接信息、域名与地址集合，以及具有明确输入前提和结果约定的策略片段。共享片段自身不拥有平台的全局入口、DNS 流程或最终默认动作。

**平台程序**描述完整处理方式。Surge 程序组织策略与 HTTP 处理；mihomo 程序组织 provider、组与路由；sing-box 程序组织入口、出口、endpoint、DNS 和路由步骤。这个归纳强调各自常见的建模方式，并不表示其他平台没有类似能力，也不把 mihomo 的所有能力外推给其他 Clash 系内核。

**构建目标**把一个平台程序绑定到具体内核、操作系统平台和版本。一个程序可以构建到多个已支持版本；需要不同环境行为时，也可以有多个程序。不能靠换一个目标名字，就把 sing-box 程序自动变成 Surge 程序。

组合时采用明确的引用和顺序，不对多个对象做任意深度合并。共享策略在程序里展开成一个有序片段，平台步骤安排在片段前后；需要在片段内部穿插步骤时，将它拆成有意义的多个片段，而不是依靠远处的规则 ID 注入。

引用的可见范围也保持简单：平台程序可以使用共享定义及自己的资源；共享定义不能反向引用某个具体程序里的私有资源。共享策略需要某种出口时，可以声明一个出口需求，由程序显式绑定，编译器校验绑定对象是否满足约定。

例如，公司策略要求“能承载匹配流量，而且失败不改走其他出口”。每个平台可以绑定不同的实现，但不能绑定一个可能在能力不足时继续扫描到直连规则的组，然后仍称其满足同一要求。

## 多版本构建解决的是同一程序的版本差异

跨平台和跨版本是两类适配工作。

跨平台时，我们检查一个共享策略能否嵌入不同的执行模型。跨版本时，我们已经选定平台程序，再检查这个程序在某个版本里怎样表达、哪些机制尚不存在、哪些已经变更。

因此，多版本能力适用于所有后端。可以同时构建多个 Surge 版本，也可以同时构建多个 mihomo 或 sing-box 版本。每个目标独立生成配置和诊断，不把较新版本通过校验当成较旧版本也能使用的证据。

格式变化且行为可保持时，由适配器转换。行为无法保持时，需要显式的版本分支或构建失败。同一个版本号在不同操作系统或不同产品中也不代表相同能力，目标身份必须包含这些条件。

版本知识属于后端适配器：记录依据、适用范围和实际验证的版本。业务策略不应该到处出现对原生字段的版本判断；必须改变行为时，再把选择暴露给用户。

## Warning 解释差异，不能替代缺失的执行机制

某个目标不能展示节点图标，可以省略图标并警告。某个版本不支持一个影响后续路由判断的解析动作，省略它就改变了程序，不能同样处理。

我们据此区分四种结果：

| 结果 | 处理方式 |
| --- | --- |
| 能保持约定行为 | 正常生成，必要时记录格式转换 |
| 只能省略已知不影响网络行为的展示信息 | 生成并 warning，指出具体损失 |
| 缺少必需行为，或无法确认语义兼容 | error，阻止该目标输出 |
| 用户已经明确限定功能只属于另一个程序 | 不适用，报告选择结果，不当作编译器自动降级 |

用户明确选择不同目标使用不同策略时，也可以正常构建，但报告应说明它们的行为不同。构建器不能先自动改掉行为，再用一行 warning 把责任推给用户。

一个具体反例是 UDP：mihomo 文档说明，UDP 请求遇到不支持 UDP 的代理节点时可能继续向下匹配。因此，“命中代理规则，后面还有直连默认动作”不能仅凭规则文字判断为失败不直连。[mihomo 规则优先级](https://wiki.metacubex.one/en/config/rules/#priority)

共享策略如果要求命中后终结，就要检查可能选中的出口及目标执行行为；平台程序如果明确采用原生的继续匹配行为，则保留该语义。两种选择都可以表达，但不能混为同一种承诺。

## 编译器怎样保留这些区别

编译首先读取共享定义与平台程序，再检查引用、顺序、输入前提和资源依赖。共享片段随后被落实到所选平台，形成该平台自己的内部表示。版本适配器在这个结构上生成目标版本的原生配置。

共享部分可以拥有公共内部表示；完整的平台程序不必全部放入同一个万能模型。sing-box 的非终结动作仍然是非终结动作，Surge 的 HTTP 处理仍然属于 HTTP 处理。

这使编译器能够解释输出来自哪里：哪条原生规则来自公司策略，哪个处理步骤由网关配置引入，哪个字段因版本不同而换了一种表达。排错时，用户既能看原生配置，也能回到源头，而不是面对无法追踪的模板拼接结果。

构建器只在构建期工作，不成为新的流量转发服务。连接、DNS 查询、订阅刷新和脚本执行仍由目标客户端完成。原生配置检查证明的是配置被接受；关键行为还要用真实内核验证，不能由输出格式正确来替代。

## 这样做究竟省了什么

回到最初的公司网络例子。

新增一个公司域名，修改共享列表即可；更换代理服务器，修改共享连接描述即可；调整“公司流量失败不得直连”的策略，需要检查每个目标绑定，但不必重新维护三份规则文本。

网关新增嗅探步骤，只修改 sing-box 程序。电脑新增 HTTP 改写，只修改 Surge 程序。升级某个客户端版本，改动相应构建目标并查看诊断，不要求其他程序跟着升级。

我们仍然维护多份平台程序，但把重复的业务内容从中抽走。平台程序保留的差异，本来就需要用户作出不同决定。把这些差异藏进自动转换，并不会让它们消失。

与分别写几份 TypeScript 模板相比，这套工具增加的价值是共同语义校验、引用检查、版本知识和可追踪诊断。如果它最终只能更方便地拼接字符串，那么普通模板就足够了，没有必要引入更大的语言系统。

## 我们也要限制这套抽象的规模

这一方向的代价是需要维护后端语义与版本证据，用户使用高级功能时也仍需理解对应平台。不能承诺学会几个通用名词，就能无损表达所有客户端的全部功能。

因此，第一步应当验证三个具体场景：

1. 同一份静态节点与域名分流，在三个目标上保持声明的行为，明确覆盖域名缺失、UDP 和失败不直连。
2. sing-box 程序加入嗅探与解析步骤后，能够直接描述执行顺序，并指出共享策略使用了哪些输入信息；无需大量前后插入补丁。
3. Surge 的 HTTP 处理、mihomo 的动态 provider 作为平台机制保留下来，版本或目标不支持时给出明确结果，不自动变成另一种功能。

如果第一种场景都需要大量平台分支，说明共享策略的约定选得不合适，应缩小范围。如果第二、三种场景只能靠随意拼接原生配置实现，说明平台模型还没有真正建立起来。

对于只使用单一客户端、配置短且稳定的用户，原生配置可能更省事。proxylang 主要服务于重复维护资源、跨平台复用策略、同时支持多个版本的场景。

## 这对现有设计意味着什么

之前的草案围绕一份公共配置，再把平台能力作为扩展插进去。本文提出的调整是让平台程序成为完整配置的拥有者，共享资源和策略以可组合片段进入其中。

节点、匹配条件、引用检查、多版本目标和诊断规则仍可保留。需要重新设计的是顶层组织方式、共享片段的输入与出口约定，以及平台程序如何绑定这些约定。原有依靠规则锚点插入扩展的方式，不再作为表达平台主流程的基础。

本文是这次方向调整的说明，尚不是新接口定案。后续设计应沿着这些机制补齐具体契约，再进行独立设计审查；此前草案的审查结果不覆盖这次架构调整。
