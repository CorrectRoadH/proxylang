# proxylang 项目原则

proxylang 服务下游作者：个人或小团队，用一份 TypeScript 代码维护多台设备的代理配置。设备使用不同客户端，出口和隧道也各不相同。设计以一个真实的多设备配置仓库为主要使用方。下面的原则既是设计判断标准，也是作者写配置时应该形成的心智模型。

## 心智模型

## T-1 一台设备一份 Profile {#t-1}

作者面对的单位是设备。一份 [Profile](concepts.md#profile) 声明一台设备的目标客户端、出口资源、有序路由、默认出口和该客户端专属的设置，构建后得到一个原生配置文件。

- 好：读 `devices.ts` 就能知道有哪些设备、各自用什么客户端、引入了哪些规则。
- 坏：让作者先理解 program、target、plan 等多层对象，才能对应到一台设备。

## T-2 复用交给 TypeScript {#t-2}

规则、节点、分组都是普通值。跨设备复用靠 `import`、数组、函数和展开；嵌套数组按顺序展开。SDK 不提供第二套模板语言，也不提供槽位或实例化语法。

- 好：`createGroups(entries, homeTunnel)` 这种使用方自己写的函数，按设备生成分组。
- 坏：SDK 内置 policy/use/slot 这类模板机制，与 TypeScript 函数做同一件事，还要再学一套规则。

## T-3 引用写对象，绑定靠函数参数 {#t-3}

路由的 `to`、分组的 `members`、节点的 `via`、`fallback` 和路由案例的 `expect` 都直接引用资源对象，不写 id 字符串。共享路由写成函数，参数是它需要的[出口](concepts.md#exit)；每台设备用自己的分组、节点或隧道调用这个函数。设备漏绑出口时，TypeScript 在编辑器里直接报错。内置的直连和拒绝写成 `outbound.direct` 与 `outbound.reject`。

- 好：`sharedRoutes({ ai, home, proxy })`；手机传入 Tailscale 隧道作为 `home`，网关传入直连分组。
- 坏：路由写 `to: "home"`，拼错成 `"hmoe"` 时，要等到运行 check 才发现；或者共享规则直接引用某台设备的节点对象，换一台设备只能复制整段规则。

## T-4 首条命中，顺序就是语义 {#t-4}

路由按作者写下的顺序生成，第一条命中的路由决定出口，都不命中时使用 `fallback`。proxylang 不按类型重排，不合并，也不去重。

- 好：内网规则写在开发规则前面，生成的配置也是这个顺序。
- 坏：为了跨平台输出，悄悄把 IP 规则挪到域名规则后面。

## T-5 引擎差异写在明处 {#t-5}

同一个逻辑对象在不同客户端上的实现，比如自动选择算法或远程规则集的来源，由作者为每个[引擎](concepts.md#engine)分别写出。目标引擎没有对应实现时报错，不自动替换成别的机制。

- 好：`group.auto()` 在 Surge 上编码为 Smart，在 sing-box 上编码为 URLTest，并在 check 输出里写明实际选择；规则集同时给出 Surge 与 sing-box 的来源。
- 坏：sing-box 设备另外维护一张“Surge URL 对应 sing-box URL”的映射表，再写测试检查有没有漏项。

## T-6 精确目标，拒绝而不降级 {#t-6}

[目标](concepts.md#target)由引擎、平台和精确版本组成，能力按目标判断。影响流量的行为在目标上不受支持时是 error；只影响展示的差异可以是 warning。proxylang 不删除规则，也不把一种机制替换成另一种。

- 好：iOS 上使用 `processName` 直接报错，并指出是哪条路由。
- 坏：在 iOS 输出里静默跳过进程规则。

## 开发体验

## T-7 错误一次报全，指向作者写的位置 {#t-7}

`check` 一次运行报告全部问题。每条诊断带稳定的错误码，指出哪份 Profile、什么资源或第几条路由，能取得定义位置时还给出源码文件和行号。诊断不回显秘密值或节点凭据。

- 好：`UNLISTED_EXIT  phone  routes[12].to  group "claude" 没有列在 groups 中  proxy/routes.ts:47`。
- 坏：返回 `COMPILATION_FAILED`，作者只能二分注释代码来定位问题。

## T-8 常见写法最短，类型先于运行时 {#t-8}

最常写的东西用最少的字：一组域名用一次调用和一个数组写完，常用选项可以批量给出。只对某个引擎有效的字段，在 TypeScript 类型里就和该引擎的目标绑定，能在编辑器里拒绝的输入不留给运行时。

- 好：`match.domainSuffix(["ai.example", "chat.example"], { includeSniffed: true })`。
- 坏：二十行 `match.domainSuffix(x, { includeSniffed: true })`；或者 Surge Profile 里写 `singBox` 字段，直到运行 check 才报错。

## T-9 一个概念一种写法 {#t-9}

同类资源使用同一组字段。每个资源有稳定的 `id`，用于诊断、案例结果和原生配置中的内部引用；`name` 设置在客户端里显示的名字。同一件事不提供两种写法，也不在别处再放一份映射。

- 好：隧道自己带 `name: "Tailscale"`。
- 坏：分组用 `name`，节点用 `label`，隧道的显示名放在 `surge.names` 映射里。

## T-10 用请求案例表达路由意图 {#t-10}

“这个域名必须走 Home”这类意图写成[路由案例](concepts.md#route-case)：给出请求，断言首条命中的出口。`check` 和 `build` 都会执行案例，案例失败就不发布。不要用字符串去匹配生成的配置文本来表达意图。

- 好：在设备的 Profile 里写 `{ name: "影视服务走 Home", request: { domain: "media.home.example" }, expect: home }`。
- 坏：读取 `out/phone.conf`，断言 `[Rule]` 段前两行是某段文本。

## T-11 生成结果确定、可审阅 {#t-11}

同样的输入每次生成字节相同的文件。生成配置的结构与源码对应：一条路由对应一条原生规则；需要展开时，按文档写明的规则展开。审阅生成结果的 diff，就能看出这次改动对设备的影响。

## T-12 为下游作者设计，用真实配置验证 {#t-12}

proxylang 面向所有用 TypeScript 维护代理配置的下游作者。能力按这类作者普遍的需求设计，而不是只按维护者自己用到的那部分；一个能力维护者不用，但其他作者需要，就应该提供。真实的多设备配置仓库用来检验能力在真实规模下是否好用，不决定能力边界。

每项能力都要有清楚的 Use Case，并在它支持的每个目标上有可执行的验证：生成结果比对，以及能做到时的原生检查。没有验证手段的部分要在文档中写明。

- 好：Mihomo 后端维护者自己不用，但它是常见的客户端，所以和 Surge、sing-box 一样接入 Profile，并在 CI 中用固定版本做原生检查。
- 坏：只因为维护者自己的设备不用，就删除别人常用的引擎；或者为了“看起来通用”加入一个没有 Use Case、也没有任何验证的能力。

## 边界

## T-13 秘密只在构建批次中读取 {#t-13}

`check` 与 `explain` 不读取秘密。`build` 在一个批次里读取秘密并写出全部文件，所有 Profile 都成功后才切换活动产物，任何失败都保留旧产物。生成配置不等于部署，部署由使用方负责。

## T-14 契约与证据分开陈述 {#t-14}

Concord 管理产品契约以及它与源码、测试的关系。单元测试、生成结果比对、原生客户端检查、使用方验收和真实网络验收各自说明能证明什么，不互相替代。
